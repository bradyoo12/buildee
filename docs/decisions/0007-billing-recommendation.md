# ADR-0007: 청구 추천 — 자연어 추천 + 표준 비교 표

**상태**: Accepted (MVP)
**날짜**: 2026-05-03
**관련 Issue**: 청구 / 정산 모듈 issue 추후 발행

## 배경

워커 라우팅 ([0002](0002-worker-tiers.md))의 결과로 사용자에게 노출되는 청구 모델이 비균질하다.

- 기본 사용자 = Buildee 정액제 (PC 워커 / API 폴백, 모두 우리 비용)
- Tier 3 옵트인 사용자 = 본인 Anthropic 키 등록 → 본인 비용 (우리 비용 0)

여기에 Buildee 자체의 요금제 (예: Free / Pro / Team)가 곱해짐. 사용자 입장에서 **"나는 어떤 조합을 써야 하는가?"** 가 매월 의사결정 사항이 되며, 잘못된 선택은 (a) 사용자가 비싼 조합을 쓰고 떠나거나 (b) 우리가 부담을 안고 마진을 잃는다.

비개발자 사용자에게 "월 토큰 X개 × $Y" 같은 숫자를 제공해도 의사결정에 도움 안 됨. **자연어로 "당신 패턴이라면 A가 적합" 형태의 추천**이 필요.

## 검토한 옵션

### A) 추천 안 함 (사용자가 알아서)
- 장: 가장 단순. 시스템 책임 없음
- 단: 비개발자 사용자에게 사실상 "고르세요" = 잘못된 선택 → 이탈

### B) 정적 비교 표만 제공
- 장: 한 번 만들면 끝
- 단: 같은 표를 봐도 "내 경우엔?" 답 못 함. 결국 A와 비슷함

### C) 단순 휴리스틱 (월 요청 수 기반 분기)
- 장: 구현 단순
- 단: 요청 수만으론 부족 (요청 1개의 사이즈 / 카테고리 분포가 비용 좌우). 잘못된 추천이 누적되면 신뢰 잃음

### D) 표준 비교 표 + 사용자 사용 패턴 분석 → 자연어 추천 ← **선택**
- 장:
  - 비교 표는 객관 사실 (변하지 않음, 검증 쉬움)
  - 추천은 표 위에 사용자 데이터를 얹어서 "당신은 지난 30일간 X 패턴, 따라서 Y 조합이 월 ~$Z" 형태
  - 자연어라 비개발자에게도 의사결정 가능
- 단:
  - 추천 정확도가 낮으면 표보다 더 위험 (잘못된 자신감 부여)
  - 사용 패턴 측정 → 추천 생성 파이프라인 새로 만들어야 함

### E) ML 기반 동적 추천
- 장: 이론적으로 정확도 최대
- 단: MVP에 ML 학습 데이터 없음. cold-start 문제. over-engineering

## 결정

**D 선택**. 두 층:

1. **표준 비교 표** — 모든 요금제 / Tier 조합을 객관 수치로 보여주는 표. 누구에게나 동일. settings / pricing 페이지에 항상 노출
2. **자연어 추천** — 사용자 본인의 지난 30일 사용 패턴을 분석해 "당신은 [요약]이므로 [조합] 추천. 예상 월 비용 ~[금액]" 형태의 한두 문장 메시지. 대시보드 / 청구 페이지에 노출

추천 메시지는 항상 **표로 검증 가능** — 사용자가 의심하면 표 보고 직접 확인. 추천이 틀려도 표는 옳음 → 신뢰 안전망.

## 구현 세부

- **표 데이터 소스**: 단일 config 파일 (`apps/server/src/billing/plans.ts`). 가격 변경 = 코드 PR (= 검토 / 추적성)
- **사용 패턴 측정**: ChangeRequest의 카테고리 분포 ([0003](0003-change-categories.md)) + 월 요청 수 + slow-path 비율 + Tier별 분배 (`ProviderHealth` 집계)
- **추천 생성**: 휴리스틱 우선 (예: slow-path 월 50건 초과 + 카테고리 다양 = "Pro + Tier 3" 추천). LLM 호출은 "메시지 자연어화" 단계만 — **분기 결정은 코드에서**, LLM은 표현만 (= 추천 일관성 / 감사 가능성 보호)
- **추천 신뢰도 표시**: "지난 30일 데이터 기준" 같은 시간 한정 명시. 신규 사용자는 추천 대신 "기본 요금제 권장" 표시
- **로깅**: 어떤 추천을 보여줬고 사용자가 따랐는지 / 따랐을 때 실제 비용이 추천 예상과 얼마나 일치했는지 기록 → 휴리스틱 iteration

## 트레이드오프

- **추천 정확도 책임** — 자연어 추천을 보여주는 순간 시스템이 "조언자" 역할. 잘못된 추천 = 신뢰 손상. 따라서 분기 로직은 코드 (감사 가능), LLM은 표현만 — 책임 경계 명확화
- **사용 패턴이 적은 신규 사용자** — 추천 못 함 = "기본 요금제" 외엔 가치 제공 못 함. 이건 어쩔 수 없음. 30일 후 첫 추천 도착하도록
- **"본인 키 쓰세요" 추천이 우리 매출 잠식** — Tier 3 옵트인 추천은 헤비 유저에 대한 우리 비용을 줄이지만, 같은 사용자의 정액제 매출도 잃음. 추천 로직은 **사용자에게 가장 저렴한 조합**을 우선 (= 우리 매출 손해도 감수). 이유: 비개발자 신뢰 = 장기 LTV 안전판. 추천이 "당신 매출 위주"로 보이면 신뢰 회복 불가
- **자연어 추천의 일관성** — 같은 사용자에게 매번 다른 표현 / 다른 추천이면 혼란. 동일 입력 → 동일 추천을 코드 분기로 보장하고, LLM 생성 메시지도 캐시 (입력이 의미 있게 변할 때만 재생성)

## 재검토 트리거
- 추천 적중률 (= 추천 따른 사용자의 실제 비용이 예상 ±20% 이내) 80% 미만 시 → 휴리스틱 재설계
- 사용자가 추천과 다른 조합을 선택한 비율이 50% 초과 시 → 추천이 사용자가 신경 쓰는 축을 못 잡고 있음. 인터뷰 / 추가 신호 도입
- 요금제 / Tier 옵션 자체 구조 변경 시 → 표 + 휴리스틱 + 추천 메시지 동시 재검토
- 사용자가 "추천이 우리 매출 위주"라는 인식을 표하면 (피드백 채널 / 리뷰) → 추천 알고리즘 투명 공개 (= 결정 근거 한 줄 노출)
- LLM 표현 비용이 추천 가치 대비 과한 경우 → 템플릿 기반으로 강등
