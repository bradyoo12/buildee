# ADR-0004: 가드레일 — 8 layer skeleton, Layer 1·2·5만 활성

**상태**: Accepted (MVP)
**날짜**: 2026-05-03
**관련 Issue**: 가드레일 layer별 issue 추후 발행

## 배경

AI가 (PC 워커든 fast-path 서버든) 사용자 사이트의 코드 / 데이터 / 운영 설정을 직접 수정한다. 사람의 코드 리뷰가 사실상 비개발자라는 게 핵심 제약 — "PR 코드 보고 승인" 같은 건 기대 못 함.

따라서 사람 리뷰 없이도 안전을 보장할 자동 가드레일이 필요. 한편 모든 가능한 검사를 MVP에 다 넣으면 출시가 무한정 미뤄진다. **무엇을 지금 만들고 무엇을 자리만 비워둘지** 결정해야 한다.

## 검토한 옵션

### A) 가드레일 없이 출시, 사고 발생 시 추가
- 장: 가장 빠른 출시
- 단: 첫 사고 = 신뢰 회복 불가. 비개발자 사용자는 "AI가 망가뜨렸다" 인식

### B) 모든 layer 일거에 구현 후 출시
- 장: 사고 가능성 최소
- 단: 출시 6개월+ 지연. 어떤 layer가 실제로 가치 있는지 데이터 없이 over-engineering

### C) 8 layer 스켈레톤 정의 + 핵심 layer만 활성, 나머지는 hook 자리만 ← **선택**
- 장: 아키텍처는 한 번에 정해두고 (= 나중에 끼워 넣기 쉬움), 활성 layer는 최소만. 데이터 보고 우선순위 결정
- 단: 비활성 layer가 false sense of safety 줄 수 있음 → 문서에 명시 필요

## 결정

**C 선택**. 8 layer 정의:

| # | Layer | 무엇을 막나 | MVP 상태 |
|---|---|---|---|
| 1 | **빌드/타입** | 컴파일 안 되는 코드, 타입 에러 | **활성** |
| 2 | **테스트** | 기존 동작 회귀, 주요 페이지 렌더 실패 | **활성** |
| 3 | 정적 분석 | 보안 패턴 (eval, dangerouslySetInnerHTML 등) | skeleton (hook만) |
| 4 | 의존성 정책 | 새 패키지 라이선스 / 알려진 CVE | skeleton |
| 5 | **도메인 룰** | "영업시간 25시", "음수 가격", "schemaVersion 역행" 등 비즈니스 불변식 | **활성** |
| 6 | 시각 회귀 | 디자인 변경 후 의도치 않은 레이아웃 깨짐 | skeleton |
| 7 | 성능 예산 | 번들 크기 / LCP 임계치 | skeleton |
| 8 | 사용자 confirm | 위험도 높은 변경 (결제 통합, DB schema 등) UI 한 단계 추가 | skeleton |

**활성 3개의 선정 근거**:
- Layer 1·2: 가장 보편적. 모든 codebase가 어떻든 필요
- Layer 5: Buildee 도메인 특화. 다른 누구도 안 해줌. **이게 우리 차별점**

## 구현 세부

- **Layer 1·2**: PC 워커가 PR 만들기 전 로컬 실행 + GitHub Actions에서 한 번 더. fast-path는 서버에서 적용 직후 검증
- **Layer 5**: `apps/server/src/guardrails/domain-rules.ts`. fast-path는 적용 전, slow-path는 PR merge webhook에서 codebase 검증. 룰 위반 시 fast는 거부 응답, slow는 PR에 자동 코멘트 + merge block
- **Skeleton layer (3·4·6·7·8)**: hook 인터페이스만 정의, 호출 지점만 표시. 구현체는 no-op + 로그
- **DecisionLog 연동**: 어떤 layer가 어느 ChangeRequest를 거부 / 통과시켰는지 전부 기록

## 트레이드오프

- **False sense of safety 위험** — 사용자 / 운영팀이 "8 layer 가드레일"이라는 표현 보고 8개 다 작동한다고 오해할 가능성. 외부 마케팅 문구 / 대시보드에는 "현재 활성 layer: 1, 2, 5" 명시. 내부 문서(`docs/`)에도 동일
- **Layer 5의 룰 누적 부담** — 도메인 룰은 새 기능마다 추가됨. 룰셋 자체가 사람이 검토 못 할 만큼 커지면 가드레일이 제품 진화 속도를 늦춤. 룰 카탈로그 + ownership을 일찍 만들어 둘 것
- **Layer 6/7 부재의 사용자 영향** — 디자인 변경이 가끔 깨지거나 페이지가 무거워질 수 있음. MVP 단계에서는 사용자가 직접 보고 신고 → 우리가 수정. 사고 빈도 보고 우선순위 결정

## 재검토 트리거
- 사고 분류 결과 비활성 layer가 막을 수 있었던 사고가 누적 3건 이상 → 해당 layer 활성화 우선순위 최상위
- Layer 1·2 통과율이 50% 미만이면 (워커 출력이 자주 깨짐) → 워커 prompt / 도메인 컨텍스트 강화 우선, 가드레일 추가는 후순위
- Layer 5 룰셋이 100개 초과 시 → 카탈로그화 + 메타가드레일 (룰 충돌 검사) 도입
- Closed Beta 진입 전 Layer 8 (위험 변경 confirm UI) 활성 검토
