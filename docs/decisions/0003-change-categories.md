# ADR-0003: 변경 카테고리 — CONTENT/CONFIG fast-path vs 나머지 slow-path

**상태**: Accepted (MVP)
**날짜**: 2026-05-03
**관련 Issue**: #2 (오케스트레이션 서버) 후속

## 배경

사용자가 자연어로 요청하는 "변경"은 스펙트럼이 넓다.

- "헤더 문구 '환영합니다' → '어서오세요'로 바꿔줘" — 본문 1단어
- "예약 폼에 전화번호 필드 추가" — 스키마 + UI + 검증
- "전체 디자인 톤을 더 모던하게" — 디자인 시스템 광범위 변경
- "라이브 채팅 위젯 통합해줘" — 외부 SDK 통합 + 새 패키지

이 모두를 동일하게 "Ticket → PC 워커 → PR → 사용자 승인 → merge → 배포"로 처리하면, 가장 단순한 1단어 변경도 5~10분 latency가 걸린다. 사용자 체감으로는 "버튼 누르고 한참 기다림 = 망가진 도구".

반대로 모두 fast-path로 서버에서 직접 적용하면 코드 품질 / 가드레일 / 추적성을 잃는다.

## 검토한 옵션

### A) 모두 slow-path (Ticket → PR)
- 장: 추적성 / 가드레일 / rollback 일관. 한 가지 흐름만
- 단: 1단어 텍스트 수정도 분 단위. 비개발자 사용자 체감 최악

### B) 모두 fast-path (서버에서 직접 적용)
- 장: 즉시 반영. UX 최고
- 단: 디자인 / 스키마 / 의존성 변경까지 서버가 직접 코드 수정 = 가드레일 우회. 잘못된 변경 누적 시 codebase 부패

### C) 사용자가 직접 모드 선택
- 장: 구현 단순 (분류기 불필요)
- 단: 비개발자 = "fast vs slow"를 판단 못 함. UI 짐 떠넘기기

### D) 분류기로 카테고리 판정 → 자동 분기 ← **선택**
- 장: 사용자는 자연어만 던짐. 시스템이 알아서 path 선택. fast-path 카테고리는 즉시 반영, slow-path는 검토 흐름
- 단: 분류 정확도가 사용자 만족도에 직결. 오분류 시 UX 손상 (fast로 보낼 게 slow로 가면 답답함, 그 반대는 가드레일 누락)

## 결정

**D 선택**. 카테고리 정의:

| 카테고리 | path | 설명 | 예 |
|---|---|---|---|
| **CONTENT** | fast | 보이는 텍스트 / 이미지 src / 링크 URL | "헤더 문구", "이 사진을 다른 걸로" |
| **CONFIG** | fast | 운영 설정 (영업 시간, 이메일 수신자, 폼 알림 대상 등) | "예약 알림을 sales@ 로", "토요일 휴무" |
| **DESIGN** | slow | 디자인 시스템 / 레이아웃 / 컴포넌트 구조 | "톤 모던하게", "히어로 섹션 다시" |
| **STRUCTURE** | slow | 페이지 추가/제거, 라우팅, 스키마 | "About 페이지 추가", "예약 폼에 필드" |
| **INTEGRATION** | slow | 외부 SDK / API / 새 패키지 | "라이브 채팅 위젯", "Stripe 결제" |
| **AMBIGUOUS** | slow (보수) | 분류기가 신뢰도 낮게 판정 | — |

분류 신뢰도가 임계치 미만이면 무조건 slow-path (= 보수적 기본값. 잘못된 fast 적용보다 약간 느린 게 낫다).

## 구현 세부

- **`POST /change-requests`** 진입점에서 분류기 호출 → `ChangeRequest.category` 저장
- **분류기**: 별도 system prompt 파일 (`apps/server/src/prompts/classifier.md`)로 분리. iteration 추적을 위해 git에 두고 prompt 변경도 PR로
- **fast-path 적용 주체**: 서버. CONTENT는 PageComposition / SpecVersion 직접 갱신 후 새 버전 INSERT ([0005](0005-immutable-versions.md)). CONFIG는 해당 설정 모델만 갱신
- **fast-path도 가드레일 layer 5 (도메인 룰)는 통과해야 함** — 예: "예약 가능 시간을 25시로" 는 거부 ([0004](0004-guardrails.md))
- **slow-path**: Ticket 생성 → GitHub Issue 자동 발행 → PC 워커 픽업 → PR
- **`DecisionLog`**: 분류 결과 + 신뢰도 + 분기된 path 기록. 오분류 사후 분석용

## 트레이드오프

- **분류 오류 비용 비대칭** — fast로 잘못 보내면 가드레일 누락 위험, slow로 잘못 보내면 단순 latency 증가. 따라서 임계치는 의도적으로 보수적 (= slow 쪽으로 기울임). 사용자 불만 ("왜 이렇게 오래 걸려요") < 코드 품질 사고
- **CONFIG 카테고리 경계 모호** — "메일 수신자" = CONFIG (fast)지만 "메일 템플릿 디자인" = DESIGN (slow). 사용자에게는 차이가 안 보임. 분류 결과를 UI에서 한 줄로 노출 ("이 변경은 즉시 반영됩니다 / 검토 후 반영됩니다") 해서 기대치 정렬
- **분류기 비용** — 매 요청 1회 LLM 호출. 토큰은 적지만 fast-path latency에 200~500ms 추가. 캐시 / 휴리스틱 단축은 일단 보류 (정확도 우선)

## 재검토 트리거
- 분류 오답률이 5% 초과 시 → prompt iteration 또는 카테고리 재정의
- fast-path 카테고리에서 가드레일 사고 발생 시 → 즉시 해당 카테고리 slow로 강등
- 사용자 피드백에서 "fast인데 왜 안 됨" / "이건 즉시 반영돼야 하는데 검토 흐름" 패턴 누적 시 → 카테고리 경계 재설계
- 분류기 latency가 fast-path 전체 latency의 50% 초과 시 → 휴리스틱 단축 도입
